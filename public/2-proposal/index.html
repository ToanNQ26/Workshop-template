Proposal

AI Web Chat on AWS with EC2, RDS and Amazon Bedrock

A cost-conscious and maintainable cloud architecture for an AI Web Chat

1. Executive Summary

This proposal presents the architecture of an AI-integrated Web Chat deployed on Amazon Web Services. The system allows users to register, sign in, create conversations and interact with an AI assistant through a web interface.

The application Backend runs on Amazon EC2, providing a stable and flexible environment for the application runtime, libraries and business logic. EC2 connects to Amazon RDS, a relational database used to store users, conversations and messages with a structured data model. Amazon Bedrock provides access to foundation models without requiring the project to manage GPU infrastructure.

The frontend is hosted on Amazon S3 and distributed through Amazon CloudFront. Amazon API Gateway can be used as the public API layer in front of the Backend. Amazon CloudWatch monitors logs, metrics and operational issues across the system.

This hybrid architecture is appropriate for the project because it combines the control of EC2, the relational capabilities of RDS and managed AWS services for delivery, AI and monitoring.

2. Problem Statement

Current challenges

  • Backend runtime requirements: The application needs a predictable environment for its runtime, dependencies and API logic.
  • Structured data management: Users, conversations and messages have clear relationships and benefit from transactions, constraints and SQL queries.
  • AI integration: The system needs to send user prompts to an AI model while controlling token usage, response length and cost.
  • Secure public access: The frontend must communicate with the Backend through protected HTTPS API endpoints.
  • Operations and troubleshooting: Logs, metrics and database health must be visible during development and testing.

Proposed solution

The system uses a hybrid cloud architecture with four main processing flows:

  1. Flow A - Frontend Distribution: The frontend is built as static assets, stored in Amazon S3 and distributed through Amazon CloudFront.
  2. Flow B - API and Backend Processing: The user sends an HTTPS request through Amazon API Gateway. The request is routed to the Backend running on Amazon EC2.
  3. Flow C - AI Chat Processing: The Backend validates the request, reads the required conversation context from RDS, calls Amazon Bedrock and stores the user message and AI response in RDS.
  4. Flow D - Data and Monitoring: Amazon RDS stores relational application data. CloudWatch collects logs and metrics from EC2, RDS, API Gateway and the application.

Benefits

  • Runtime control: EC2 allows the project to choose the operating system, runtime, libraries and application configuration.
  • Data consistency: RDS supports relational schemas, transactions, foreign keys and clear conversation history queries.
  • Flexible growth: EC2 can be resized or combined with Auto Scaling as request volume grows. RDS can be scaled and configured for Multi-AZ when required.
  • Managed AI integration: Amazon Bedrock provides model access without deploying or maintaining GPU infrastructure.
  • Operational visibility: CloudWatch provides logs and metrics for EC2, RDS, APIs and application errors.

Main processing flows

1. Flow A - Frontend Distribution
  • A1: The user opens the Web Chat in a browser.
  • A2: CloudFront receives the request and distributes frontend assets.
  • A3: The built frontend files are stored in Amazon S3.
  • A4: CloudFront caches suitable content to improve load performance and reduce direct requests to S3.
2. Flow B - API and Backend Processing
  • B1: The user performs an action such as signing in, creating a conversation, sending a message or loading history.
  • B2: The frontend sends an HTTPS request to Amazon API Gateway.
  • B3: API Gateway routes the request to the Backend running on EC2.
  • B4: The Backend validates the request, applies business logic and communicates with RDS, Bedrock or other AWS services.
3. Flow C - AI Chat Processing
  • C1: The user enters and submits a message.
  • C2: API Gateway forwards the request to the EC2 Backend.
  • C3: The Backend verifies the user and prepares a prompt with the required conversation context.
  • C4: Amazon Bedrock processes the prompt using the selected foundation model.
  • C5: The AI response is returned to the Backend.
  • C6: The Backend stores the user message and AI response in RDS.
  • C7: The response is returned through API Gateway and displayed in the Web Chat.
4. Flow D - Data and Monitoring
  • D1: Amazon RDS stores users, conversations and messages in related tables.
  • D2: The EC2 Backend writes logs while processing requests.
  • D3: CloudWatch collects logs and metrics from EC2, RDS, API Gateway and the application.
  • D4: CloudWatch is used to monitor EC2 CPU and memory, RDS connections, request counts, errors and application health.

AWS services

  • Amazon S3: Hosts the frontend and static assets.
  • Amazon CloudFront: Distributes frontend content through a CDN.
  • Amazon API Gateway: Provides public API endpoints and routes requests to the Backend.
  • Amazon EC2: Runs the Backend and provides the application runtime environment.
  • Amazon RDS: Provides a relational database for users, conversations and messages.
  • Amazon Bedrock: Provides AI inference for the Web Chat.
  • Amazon CloudWatch: Provides logging, monitoring and operational metrics.
  • AWS IAM: Controls access between AWS services using the Least Privilege principle.

4. Technical Implementation

Implementation phases

  1. Phase 1: Research and architecture design

    • Analyze Web Chat requirements and define core features.
    • Design the AWS architecture and request flows.
    • Select the required AWS services.
    • Design the relational data model for Amazon RDS.

  2. Phase 2: Backend development on EC2

    • Create and configure an EC2 instance.
    • Install the application runtime, libraries and Backend application.
    • Configure Amazon RDS and its relational schema.
    • Build user, conversation and message APIs.
    • Configure the EC2 IAM role, Security Group and environment variables.

  3. Phase 3: AI integration

    • Request and configure access to Amazon Bedrock.
    • Select a model based on requirements and budget.
    • Integrate Bedrock with the EC2 Backend.
    • Design prompts and handle AI responses.
    • Store conversation history in RDS.
    • Limit prompt and response length to control cost.

  4. Phase 4: Frontend and deployment

    • Complete the Web Chat interface and build the frontend.
    • Upload static assets to S3 and configure CloudFront.
    • Connect the frontend to API Gateway.
    • Test sign-in, conversation creation and AI chat flows.

  5. Phase 5: Monitoring, testing and optimization

    • Configure CloudWatch Logs and metrics.
    • Monitor EC2, RDS and API requests.
    • Test API endpoints and the AI message flow.
    • Test concurrent requests and database behavior.
    • Review AWS usage and costs.
    • Optimize EC2, RDS and Bedrock usage.
    • Complete the internship report and technical documentation.

Technical and security requirements

  • Use an IAM Role for EC2 and avoid storing Access Keys in source code.
  • Apply Least Privilege to EC2, RDS, Bedrock and monitoring permissions.
  • Use Security Groups to restrict access to the application and database ports.
  • Keep RDS private where possible and allow database access only from the Backend.
  • Use HTTPS for communication between the client, API layer and Backend.
  • Validate input and authenticate requests before executing business logic.
  • Limit prompt size, response length and AI requests to control cost and abuse.
  • Send application and infrastructure logs to CloudWatch.
  • Store passwords securely using a suitable password-hashing mechanism.

6. Estimated Budget

The project is intended for an internship prototype with low traffic. The final cost depends on the EC2 instance type, RDS database engine, storage, running time, CloudFront traffic and Bedrock token usage.

AWS serviceEstimated scopeExpected cost
Amazon EC2Small instance for the BackendDepends on instance type and running time
Amazon RDSSmall database instance and test storageDepends on engine, instance and storage
Amazon API GatewayLow API request volumeLow usage-based cost
Amazon S3Frontend and static assetsLow usage-based cost
Amazon CloudFrontLow trafficLow usage-based cost
Amazon CloudWatchLogs and monitoringDepends on log volume and retention
Amazon BedrockAI inferenceDepends on model and token usage

Cost control measures: choose small EC2 and RDS configurations, stop or delete unused resources, monitor running time and storage, limit Bedrock requests and tokens, review AWS Billing regularly and clean up test resources after each phase.

8. Expected Results

  • A working AI Web Chat that allows users to interact with an AI assistant.
  • A Backend deployed on Amazon EC2 with APIs for users, conversations and messages.
  • Relational application data stored in Amazon RDS.
  • AI responses generated through Amazon Bedrock.
  • Frontend hosted on Amazon S3 and distributed through Amazon CloudFront.
  • CloudWatch monitoring for logs, metrics and operational issues.
  • IAM, Security Groups and private database access applied to improve security.
  • Practical experience with AWS Core Services, Networking, EC2, RDS, Monitoring and AI Services.

Conclusion

This proposal aims to build an AI-integrated Web Chat on AWS using a hybrid architecture. Amazon EC2 provides the Backend runtime, Amazon RDS manages relational data, and Amazon Bedrock provides AI capabilities. S3, CloudFront, API Gateway, CloudWatch and IAM complete the frontend delivery, API management, monitoring and security layers.

The architecture can be adjusted during implementation based on functional requirements, performance, resource usage and actual cost. The initial scope prioritizes a small, secure and testable prototype suitable for an internship project.
